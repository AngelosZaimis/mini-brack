# Lens: Transactions & Hibernate

## Scope
Files: `*.java` under `src/main` (entities, services, repositories, controllers), `db/migration/*.sql`,
`application*.yml`.
Related ADRs: 0001 (Flyway owns schema, `ddl-auto: validate`), 0002 (UUID v7 ids generated by the app).
Context: `open-in-view: false`, so lazy loading outside a transaction fails.

## Checks

### Transaction boundaries
- Look for: `@Transactional` on controllers or repositories instead of the service method that forms one business
  operation; a use case doing several writes with no transaction; reads without `readOnly = true`.
- Skip when: a single Spring Data call (repositories are already transactional per method).
- MiniBrack anchor: "create product + initial price + stock" is one unit of work.
- Ask yourself: "If the second write fails, should the first one stay?"

### Proxy pitfalls
- Look for: `@Transactional` on `private` or `final` methods; a method calling another `@Transactional` method on
  `this` (self-invocation skips the proxy); checked exceptions expected to roll back (by default only unchecked do).
- Skip when: none of these patterns appear.
- MiniBrack anchor: any service with internal helper methods.
- Ask yourself: "Does this call actually go through the Spring proxy?"

### Lazy loading and N+1
- Look for: accessing lazy associations after the service returns (→ `LazyInitializationException` with OSIV off);
  loops that trigger one query per item; `FetchType.EAGER` added to "fix" it.
- Skip when: no associations yet (single-table entities).
- MiniBrack anchor: product ↔ category, product ↔ prices once those exist.
- Ask yourself: "How many SQL statements does this endpoint run for 50 products?" (check the `org.hibernate.SQL`
  debug log locally)

### Dirty checking and `save()`
- Look for: `repository.save(entity)` on an entity already loaded in the same transaction; manual `flush()` without
  a reason.
- Skip when: new entities (`save` is how you persist them) or detached ones.
- MiniBrack anchor: updating product name/price.
- Ask yourself: "Is this entity managed right now? What would happen without `save`?"

### Concurrent updates
- Look for: read-modify-write on shared counters (stock, deal quantity) with no `@Version` or lock; lost-update risk.
- Skip when: data edited by one admin at a time with no contention (a plain update is fine, maybe add `@Version` later).
- MiniBrack anchor: flash deals, stock decrement under load. This becomes critical in week 2/3.
- Ask yourself: "Two requests read stock = 1 at the same time. What happens?"

### Entity design
- Look for: `equals`/`hashCode` from Lombok `@Data`/`@EqualsAndHashCode` or over all fields; public no-arg
  constructor; public setters for everything; id not generated per ADR 0002.
- Skip when: the entity has no identity semantics yet beyond the id and no collections use it.
- MiniBrack anchor: `Product`.
- Ask yourself: "Is this entity equal to itself before and after persist? In a `HashSet`?"

### Schema vs entity
- Look for: entity columns, types, lengths or nullability that don't match the migration (fails at startup under
  `validate`); schema change done by editing an applied migration instead of a new one.
- Skip when: entity and migration added together and consistent.
- MiniBrack anchor: `V1__create_product.sql` ↔ `Product`.
- Ask yourself: "Would this boot against a database that already ran every previous migration?"

### Work inside transactions
- Look for: HTTP calls, Kafka sends or long computations inside a DB transaction (holds connections and locks;
  event may be sent while the DB rolls back).
- Skip when: nothing external is called.
- MiniBrack anchor: "product changed" events → outbox pattern (week 2).
- Ask yourself: "If the commit fails after the event is sent, what does the consumer believe?"
